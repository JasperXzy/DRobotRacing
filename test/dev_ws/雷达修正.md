# lidar_location 雷达运动补偿与 12 Hz 定位修正实施方案

## 1. 目标与边界

当前系统使用 `lidar_location` 完成 `map` 坐标系下的二维雷达定位：

```text
N10 雷达 12 Hz -> /scan -> lidar_location -> map -> odom
底盘轮速 + MPU6050 -> robot_localization EKF 50 Hz -> odom -> base_link
```

本次改造需要解决两个问题：

1. 一圈雷达约需要 `1 / 12 = 83 ms`，车辆在采集期间仍在运动，整圈点不能视为同一时刻。
2. 雷达只能提供 12 Hz 的全局观测，不能直接满足 50 Hz 控制对连续位姿的需求。

本方案遵循以下边界：

- EKF 继续负责高频局部运动，不把雷达位姿直接反馈进当前 EKF，避免形成 TF 闭环。
- 雷达只负责低频全局修正 `map -> odom`。
- 运动补偿在 `lidar_location` 内部对笛卡尔点执行，不把补偿后的点重新伪装成规则 `LaserScan`。
- 第一版不修改 `/scan` 的角度和距离接口，保证现有避障节点继续工作。
- 不能同时运行其他 `map -> odom` 发布者，例如 AMCL；本方案本身不启动也不使用 AMCL。

### 1.1 位姿话题命名先消除歧义

当前配置中的 `pose_topic: /amcl_pose` 只是早期兼容名称，实际发布者一直是
`lidar_location`，不代表系统运行了 AMCL。源码检索没有发现任何运行节点订阅
`/amcl_pose`，路径跟随器使用的是 TF。因此本方案实施时首先将其改名为：

```yaml
pose_topic: /lidar_location/pose
```

需要同步修改：

```text
/root/D_Robot/test/dev_ws/src/origincar_system/config/localization/lidar_location.yaml
/root/D_Robot/test/dev_ws/src/lidar_location/config/lidar_location.yaml
/root/D_Robot/test/dev_ws/src/lidar_location/src/lidar_location_node.cpp
```

后文统一使用 `/lidar_location/pose`，不再沿用 AMCL 的话题名称。

## 2. 当前代码中的直接问题

### 2.1 雷达驱动已有时间信息

文件：

```text
/root/D_Robot/test/dev_ws/src/lidar_driver/src/lidar_driver.cc
```

驱动已经填写：

```cpp
scan->header.stamp = start_time;
scan->scan_time = scan_time;
scan->time_increment = scan_time / (count_num - 1);
```

因此可以获得整圈起始时间和名义逐束间隔。

### 2.2 ranges 下标与采样时间顺序相反

驱动使用：

```cpp
point_idx = round((360 - points[i].degree) * count_num / 360);
```

原始角度随采样过程增加，而发布数组下标随原始角度减小。当前全 360 度配置下，应先按以下关系计算束时间：

```text
t_i = t_start + (N - 1 - i) * time_increment
```

这里的 `i` 是 `/scan.ranges` 的下标。实现后必须通过实车录包验证首尾束顺序；没有验证前不要改成正序。

### 2.3 定位节点忽略逐束时间

文件：

```text
/root/D_Robot/test/dev_ws/src/lidar_location/src/lidar_location_node.cpp
```

当前 `scan_points_in_base()` 使用一个静态 `laser -> base_link` 变换处理整圈点，未使用 `scan_time` 和 `time_increment`。`scan_callback()` 又使用扫描起始时刻的 `odom -> base_link` 作为整圈位姿。

当前 `lidar_location` 位姿话题的时间戳是 `now()`，但它表达的实际观测时间不是
`now()`。改名后的 `/lidar_location/pose` 必须使用真实观测参考时刻，否则高速或转弯时仍会形成时间偏差。

### 2.4 TF 查询失败时不能回退到 latest

当前 `lookup_transform_at()` 在指定时间 TF 不可用时回退到最新 TF。逐束补偿启用后，这会把不同时间语义混在同一帧中。修正后应当等待短时间或拒绝该帧，不能静默使用 latest。

## 3. 目标数据流

```text
                         +------------------------------+
/chassis/odom ---------->|                              |
/chassis/imu/data_raw -->| EKF 50 Hz                    |--> odom -> base_link
                         +------------------------------+
                                        |
                                        | TF 历史
                                        v
/scan 12 Hz --> 逐束时间恢复 --> SE(2) 去畸变到扫描结束时刻
                                        |
                                        v
                              地图扫描匹配
                                        |
                                        v
                              候选 map -> odom
                                        |
                          分数/位移/航向/连续帧门控
                                        |
                                        v
                              平滑后的 map -> odom
                                        |
                                        v
                最新 map -> odom * 最新 odom -> base_link
                                        |
                                        v
                              50 Hz 连续控制位姿
```

12 Hz 的限制不能通过生成虚假雷达帧消除。正确方式是用 50 Hz EKF 在雷达帧之间传播，只在新雷达到达时修正全局误差。

## 5. 第二阶段：实现逐束运动补偿

### 5.1 新增参数

修改：

```text
/root/D_Robot/test/dev_ws/src/origincar_system/config/localization/lidar_location.yaml
```

第一版建议加入：

```yaml
lidar_location:
  ros__parameters:
    pose_topic: /lidar_location/pose

    deskew_enabled: true
    deskew_reference: end
    deskew_scan_time_order: reverse
    deskew_tf_bins: 10
    deskew_min_scan_time: 0.04
    deskew_max_scan_time: 0.12
    deskew_tf_wait_timeout: 0.04
    deskew_require_full_tf: true

    correction_gate_enabled: true
    correction_max_translation: 0.30
    correction_max_yaw_deg: 12.0
    correction_large_translation: 0.12
    correction_large_yaw_deg: 5.0
    correction_confirmation_frames: 2

    correction_smoothing_enabled: true
    correction_max_linear_rate: 0.50
    correction_max_angular_rate_deg: 60.0
    correction_deadband_translation: 0.005
    correction_deadband_yaw_deg: 0.2

    tf_publish_rate: 50.0
```

这些值只是首次实车测试起点。不要在没有 rosbag 对比的情况下直接视为最终参数。

### 5.2 新增数据结构

在 `LidarLocationNode` 中增加：

```cpp
struct TimedBeam
{
  std::size_t index{0};
  double range{0.0};
  double angle{0.0};
  double offset_seconds{0.0};
};

struct DeskewResult
{
  std::vector<cv::Point2f> points_in_reference_base;
  rclcpp::Time reference_stamp;
  tf2::Transform odom_to_base_reference;
  double tf_coverage{0.0};
};
```

同时增加以下成员状态：

```text
map_to_odom_estimate_   已接受的内部定位估计，用于下一帧匹配预测
map_to_odom_published_  经过速率限制后发布给控制系统的修正
map_to_odom_target_     最近一次通过门控的目标修正
last_tf_update_time_    平滑器上次更新时间
pending_large_count_    大修正确认帧数
```

内部估计和发布值必须分开。否则发布端平滑会让下一帧匹配仍从落后位置开始，反复计算同一修正。

### 5.3 恢复每束时间

新增函数：

```cpp
bool build_timed_beams(
  const sensor_msgs::msg::LaserScan & scan,
  std::vector<TimedBeam> & beams,
  rclcpp::Time & scan_start,
  rclcpp::Time & scan_end);
```

处理顺序：

1. 检查 `ranges.size() >= 2`。
2. 优先使用 `scan.scan_time`，无效时才使用 `time_increment * (N - 1)`。
3. 检查扫描时长是否处于允许范围。
4. `scan_start = header.stamp`。
5. `scan_end = scan_start + scan_duration`。
6. 对有效距离束计算角度。
7. 当前驱动全 360 度配置使用反序时间。

反序公式：

```cpp
const double ratio =
  static_cast<double>(scan.ranges.size() - 1 - index) /
  static_cast<double>(scan.ranges.size() - 1);
beam.offset_seconds = ratio * scan_duration;
```

如果以后修改驱动使数组与采样正序一致，则通过参数切换为：

```cpp
beam.offset_seconds =
  static_cast<double>(index) / (scan.ranges.size() - 1) * scan_duration;
```

### 5.4 补偿到扫描结束时刻

新增函数：

```cpp
bool deskew_scan_to_reference(
  const sensor_msgs::msg::LaserScan & scan,
  const tf2::Transform & base_from_laser,
  DeskewResult & result);
```

推荐统一补偿到扫描结束时刻：

```text
t_ref = scan_end
```

对第 `i` 束执行：

```text
p_base(ref) =
  inverse(T_odom_base(ref))
  * T_odom_base(t_i)
  * T_base_laser
  * p_laser(i)
```

其中：

- `T_base_laser` 是静态外参。
- `T_odom_base(t_i)` 来自 EKF 的 TF 历史。
- 输出点全部表达在 `t_ref` 时刻的 `base_link` 坐标系。

### 5.5 使用时间桶减少 TF 查询

不要对 180 束逐一阻塞查询 TF。将扫描时间分成 `deskew_tf_bins=10` 个桶：

1. 先检查扫描起点和终点 TF 是否可用。
2. 查询每个桶中心时刻的 `odom -> base_link`。
3. 每束使用最近桶，或在相邻桶之间对 `x/y/yaw` 做 SE(2) 插值。
4. 航向插值前必须先用 `normalize_angle()` 处理跨 `+-pi`。

如果起点或终点 TF 缺失：

- 最多等待 `deskew_tf_wait_timeout`。
- 仍不可用则拒绝整帧。
- 不调用当前的 latest TF 回退逻辑。

可以保留原来的 `lookup_transform_at()` 给非去畸变路径使用，但去畸变函数必须使用严格版本，例如：

```cpp
bool lookup_transform_at_strict(
  const std::string & target,
  const std::string & source,
  const rclcpp::Time & stamp,
  tf2::Transform & result);
```

### 5.6 改造 scan_callback()

`scan_callback()` 推荐改成以下顺序：

```text
检查地图和初始位姿
  -> 获取静态 base_link <- laser
  -> 构建逐束时间
  -> 等待完整扫描时间段的 EKF TF
  -> 补偿所有束到 scan_end
  -> 用 map_to_odom_estimate_ * odom_to_base(scan_end) 生成预测位姿
  -> 扫描匹配
  -> 质量和修正幅度门控
  -> 更新 map_to_odom_estimate_ 与 map_to_odom_target_
  -> 发布观测时间为 scan_end 的定位位姿
```

关键变化：

```cpp
const Pose2D predicted_pose = transform_to_pose(
  map_to_odom_estimate_ * deskew_result.odom_to_base_reference);

const MatchResult match = match_scan(
  predicted_pose, deskew_result.points_in_reference_base);
```

匹配成功后：

```cpp
const tf2::Transform candidate_map_to_odom =
  pose_to_transform(match.pose) *
  deskew_result.odom_to_base_reference.inverse();
```

`publish_pose()` 应接收明确的时间参数：

```cpp
void publish_pose(const rclcpp::Time & measurement_stamp);
```

并使用：

```cpp
message.header.stamp = measurement_stamp;
```

## 6. 第三阶段：解决 12 Hz 修正跳变

### 6.1 现有高频传播可以继续使用

当前 EKF 已按 `50 Hz` 发布 `odom -> base_link`。路径跟随器查询最新 `map -> base_link`，所以雷达两帧之间的当前位置可以由以下组合连续得到：

```text
T_map_base(now) = T_map_odom(published) * T_odom_base(now)
```

不需要把 `/lidar_location/pose` 人工插值为 50 Hz，也不需要重复发布旧扫描。

### 6.2 修正门控

对候选修正计算：

```text
delta = inverse(map_to_odom_estimate) * candidate_map_to_odom
delta_xy = hypot(delta.x, delta.y)
delta_yaw = abs(normalize_angle(delta.yaw))
```

满足以下条件才接受：

1. `match.score >= min_match_score`。
2. 有效束数量满足要求。
3. TF 覆盖率满足要求，第一版建议必须为 `100%`。
4. `delta_xy <= correction_max_translation`。
5. `delta_yaw <= correction_max_yaw`。
6. 匹配分数相对预测位姿没有明显下降。

大于 `correction_large_translation` 或 `correction_large_yaw` 的修正需要连续两帧方向和大小基本一致才接受。正常初始化后的单帧超大修正直接拒绝，并继续使用 EKF 预测。

`/initialpose` 是例外：收到人工初始化时立即重置内部估计、发布估计和待确认状态，不走大修正门控。

### 6.3 发布端速率限制

TF 定时器以 `50 Hz` 执行，每次将 `map_to_odom_published_` 向 `map_to_odom_target_` 推进：

```text
max_translation_step = correction_max_linear_rate * dt
max_yaw_step = correction_max_angular_rate * dt
```

平移沿目标误差方向限速，航向沿最短角度方向限速。误差小于 deadband 时直接保持，减少静止抖动。

首次成功定位或收到 `/initialpose` 时，允许立即初始化 `map_to_odom_published_`，避免从单位变换缓慢移动到初始位置。

## 7. 第四阶段：增强扫描匹配可靠性

运动补偿稳定后再改匹配器，避免同时改变太多变量。

### 7.1 增加预测位姿约束

当前爬山搜索最多执行 80 次，没有明确的搜索边界。应增加候选位姿相对预测位姿的限制：

```yaml
search_window_x: 0.30
search_window_y: 0.30
search_window_yaw_deg: 12.0
```

所有候选必须落在窗口内，防止在正方形场地被相似板边拉到错误解。

### 7.2 粗到细搜索

推荐两级搜索：

```text
粗搜索：地图分辨率、1.0 deg
细搜索：0.5 * 地图分辨率、0.2 deg
```

先确定稳定峰值，再局部细化。不要一开始扩大全局搜索范围。

### 7.3 增加鲁棒评分

地图中不存在的人员、圆锥和临时障碍不应直接拉偏定位。建议统计每束到最近占据栅格的距离，并增加：

- 内点距离阈值，例如 `0.20 ~ 0.30 m`。
- 内点比例。
- 中位残差和 P95 残差。
- 对大残差使用截断损失，不让少数动态点主导评分。

当前 `min_match_score: 0.05` 较宽松，但不能脱离实车分布直接指定最终阈值。应从 baseline rosbag 中统计正常匹配分数的 P10 和错误帧分数，再设置阈值。

### 7.4 动态协方差

当前 `lidar_location` 位姿始终发布固定协方差。建议让
`/lidar_location/pose` 按匹配质量调整：

```text
高分数 + 高内点率 + 尖锐峰值 -> 小协方差
低分数或宽峰值             -> 大协方差
拒绝帧                     -> 不发布新的雷达观测位姿，或明确增大协方差
```

## 10. 单元测试要求

建议将时间恢复、SE(2) 插值和点补偿提取为无 ROS 副作用的辅助函数，并至少覆盖：

1. 静止：补偿前后点完全一致。
2. 匀速直行：模拟静态墙，补偿后墙厚度减小。
3. 匀速旋转：补偿后所有点回到同一参考位姿。
4. 正序和反序时间恢复。
5. 航向跨越 `+pi/-pi` 时插值连续。
6. `scan_time=0`、负值、过大值时拒绝或使用合法备用值。
7. 起点或终点 TF 缺失时拒绝整帧。
8. 大修正必须连续确认。
9. `/initialpose` 能清空平滑器和确认状态。

如果增加 GTest，需要在 `lidar_location/CMakeLists.txt` 和 `package.xml` 中增加 `ament_cmake_gtest` 测试依赖。

## 11. 实车 A/B 测试与验收

### 11.1 测试方法

准备两套配置：

```text
baseline：deskew_enabled=false，correction_smoothing_enabled=false
candidate：deskew_enabled=true，correction_smoothing_enabled=true
```

使用相同路线、速度、电池状态和障碍摆法分别运行不少于 5 次。每次只改变一个阶段的功能。

### 11.2 验收指标

第一版建议达到：

- `/scan` 实测频率稳定在设备允许范围，时间戳单调递增。
- 12 Hz 时扫描时长主要分布在 `0.07 ~ 0.10 s`。
- 静止时补偿前后点云无明显差异。
- `1.0 ~ 1.5 m/s` 直行和转弯时，墙体残差 P95 相比 baseline 降低至少 `30%`。
- 正常路线中不出现单帧超过 `0.30 m` 或 `12 deg` 的已接受修正。
- `map -> base_link` 在 50 Hz 控制中连续，无雷达到帧时的明显瞬跳。
- 雷达修正被拒绝后，车辆仍能依靠 EKF 连续运行，并在后续有效帧恢复修正。
- 扫描处理时间应明显小于 `83 ms`，建议 P95 小于 `30 ms`。
- 完整路线连续运行 5 次，不出现定位翻转到 `90/180/270 deg` 对称解。

## 12. 异常现象与调整顺序

| 现象 | 优先检查或调整 |
| --- | --- |
| 补偿后畸变更严重 | 首先切换 `deskew_scan_time_order`，检查雷达首尾束方向 |
| 所有帧都缺少结束 TF | 增加最多 `20 ~ 40 ms` 等待，检查 EKF 时间戳，不要回退 latest |
| 直行改善但转弯仍差 | 检查 IMU `angular_velocity.z`、SE(2) 航向插值和雷达外参 |
| 雷达到帧时控制位置跳动 | 降低发布修正速率，确认内部估计与发布估计已经分离 |
| 定位长期跟不上真实位置 | 适度提高修正速率，检查门控是否长期拒绝有效帧 |
| 经常出现大修正确认 | 收紧匹配搜索窗，检查 `min_match_score` 和动态障碍离群点 |
| CPU 过高 | 先减少 `deskew_tf_bins`，再降低 `max_beams` 或匹配迭代数 |
| 静止时位置抖动 | 增大修正 deadband，检查雷达时间和外参，不先增加平滑延迟 |

## 13. 回退策略

每个阶段都必须可独立关闭：

```yaml
deskew_enabled: false
correction_gate_enabled: false
correction_smoothing_enabled: false
```

出现下列任一情况立即回退最近阶段：

- 补偿后地图残差比 baseline 增大。
- 定位线程处理时间超过一个雷达周期并持续丢帧。
- TF 查询阻塞导致控制或传感器回调停顿。
- `map -> odom` 出现比 baseline 更大的跳变。
- 完整路线出现新的航向翻转或持续定位丢失。

回退只关闭新功能，不修改 EKF、底盘标定、地图和路径跟随参数，避免同时改变多个基线。

## 14. 后续扩展：避障点云也做补偿

以上改造首先修正定位。当前路径跟随节点仍直接使用原始 `/scan` 做动态障碍和地图过滤，整圈点同样存在约 83 ms 的运动畸变。

定位稳定后，可以把去畸变模块抽成独立节点，发布：

```text
/lidar/deskewed_points  sensor_msgs/msg/PointCloud2
```

点云坐标统一表达在扫描结束时刻的 `base_link` 下，并使用扫描结束时间戳。`lidar_location` 和路径跟随器共同消费该点云。

不要把补偿后的点重新发布成普通 `LaserScan`：补偿后每个点相对参考位姿的极角会改变，不再严格落在原始等角度光束上，强行重采样会引入新的空洞和距离误差。

## 15. 推荐实际开发顺序

1. 录制 baseline，确认 `/scan` 的频率、扫描时长和反序采样关系。
2. 提取并单测逐束时间恢复和 SE(2) 点补偿。
3. 在 `lidar_location` 中启用补偿到扫描结束时刻。
4. 修正 `/lidar_location/pose` 时间戳，禁止补偿路径回退 latest TF。
5. 实车只对比去畸变效果，暂不启用平滑和新匹配器。
6. 加入修正门控，验证错误匹配不会更新 `map -> odom`。
7. 分离内部估计和发布估计，启用 50 Hz 修正速率限制。
8. 最后增加有限搜索窗、粗细搜索和鲁棒残差。
9. 定位方案稳定后，再把去畸变点云提供给避障模块。

这个顺序能把“时间错误、匹配错误、发布跳变”三个问题分开验证，出现异常时可以准确定位和回退。
