### 为什么值得尝试

- 控制逻辑完全透明，方便观察横向误差、航向误差和输出饱和。
- 可以针对固定赛道做速度分段，直道快、弯道慢。
- 不再受 Nav2 controller 的进度检查、目标检查、旋转恢复等机制干扰。
- 参数数量少，实车调试可能比 TEB 更直接。
- 如果赛道基本静态，可以只规划一次，之后稳定跟踪整条路径。

### 最大风险

普通二维 A* 不考虑阿克曼运动学，路径可能出现直角拐弯。小车再强的 PID 也无法执行这种路径。因此建议继续使用现在的 **Smac Hybrid-A***，而不是退回普通 Navfn A*。

此外，不建议逐点使用：

```text
距离 PID → 速度
目标点方位误差 PID → 转向
到达当前点 → 切换下一个点
```

这种做法容易产生：

- 路径点切换时转向突变
- 在点附近左右摆动
- 弯道“追着点跑”，切弯或冲出路径
- 积分饱和
- 当前目标落到车后方后回头追点

### 推荐控制方法

每个控制周期从整条路径中寻找：

1. 距离车辆最近、且尚未通过的路径点。
2. 沿路径向前一定距离的前视点。
3. 计算横向误差 `e_y`、航向误差 `e_yaw` 和参考曲率 `κ`。
4. 使用：

```text
转向角 = 曲率前馈 + 横向误差反馈 + 航向误差反馈
δ = atan(L·κ) + PID_y(e_y) + PID_yaw(e_yaw)
```

然后根据当前底盘接口转换为：

```text
angular.z = v · tan(δ) / L
```

速度不要只用距离 PID，而应主要根据路径曲率调节：

```text
v = clamp(v_max / (1 + k·|κ|), v_min, v_max)
```

接近终点时再叠加距离减速。

第一版甚至可以先不用积分项：

```text
δ = atan(L·κ) + K_y·e_y + K_yaw·e_yaw + K_d·de_y/dt
```

对路径跟踪而言，`I` 项很容易引起弯后反向摆动，确认存在稳定偏差后再逐渐加入。

### 建议的软件结构

```text
map + AMCL
      ↓ 当前 map→base_link 位姿
Smac Hybrid-A* → nav_msgs/Path
      ↓
路径平滑、等距重采样
      ↓
最近点 + 动态前视点
      ↓
曲率前馈 + PID反馈
      ↓
速度规划、转角限幅、加速度限幅
      ↓
/cmd_vel
```

控制节点还应具备：

- 最近点索引只能总体向前，不能在路径上反复跳动
- 转角和转角变化率限制
- PID 抗积分饱和
- 微分低通滤波
- TF 或定位超时立即停车
- 路径结束停车
- 激光检测到危险距离时停车或重新规划
- 输出独占，避免多个节点同时发布 `/cmd_vel`

### 我的判断

这个方向值得做，尤其适合作为一个独立、可解释的竞赛控制方案。但真正可能带来提升的不是“换成 PID”四个字，而是：

> **Hybrid-A* 保证路径能走，曲率前馈负责主动转弯，PID 只负责消除跟踪误差。**

如果只用普通 A* 加逐点位置 PID，稳定性很可能不如现在的 RPP；如果按上述结构实现，则很有机会比通用 Nav2 controller 更容易调到适合你们赛道的状态。建议第一阶段保留现有 Nav2 启动与规划部分，新建一个独立 follower 节点，与 RPP 做 A/B 对比。

放弃的是局部规划器，不是实时规划。PID 以 50 Hz 跟踪最近一条有效路径；Smac 在后台以 3–5 Hz 更新路径，两者互不阻塞。

### 为什么这样不会“犹犹豫豫”

局部规划器的问题通常是每个控制周期都在重新优化速度和短期轨迹，局部代价稍有变化，输出就跟着摆动。

新架构中：

```text
雷达 → global costmap（5–10 Hz）
                 ↓
         Smac 重规划（3–5 Hz）
                 ↓
     平滑、校验、防抖、路径融合
                 ↓
PID 跟踪最近有效路径（50 Hz）→ /cmd_vel
```

规划线程不会直接控制车。新路径只有在满足以下条件后才替换旧路径：

- 确实绕开了新障碍；
- 前方路径碰撞检查通过；
- 曲率可以被车辆执行；
- 与正在跟踪的旧路径衔接平滑；
- 不是由单帧雷达噪声造成的大幅改线。

即使 Smac 某一帧超时，PID 仍然沿上一条有效路径行驶，不会等待或停车。

### 实时规划参数初值

当前配置的 global costmap 已经接入 `/scan`，感知范围为 5 m，但更新频率是 5 Hz；Smac 的 `max_planning_time` 还是 5 秒，不适合这种架构。[nav2(rpp_follower).yaml](/root/D_Robot/dev_ws/config/nav2/nav2(rpp_follower).yaml:193)

我建议第一版这样设置：

```yaml
global_costmap:
  update_frequency: 10.0
  publish_frequency: 2.0

planner_server:
  expected_planner_frequency: 5.0

GridBased:
  max_planning_time: 0.15
  max_iterations: 2000
  angle_quantization_bins: 48
  minimum_turning_radius: 0.32
  cache_obstacle_heuristic: true
  downsample_costmap: false
```

其中：

- 先保留 0.05 m 地图分辨率，保证障碍轮廓准确。
- 实测规划延迟 P95 超过 200 ms，再启用 `downsampling_factor: 2`。
- 48 个方向桶是 7.5°，比当前 64 桶更快，后续平滑可以消除部分离散感。
- `expected_planner_frequency` 只是检查频率是否达标，真正的重规划由新 follower 节点定时发起。
- 同一时间只允许一个规划请求；如果旧请求还没结束，就跳过该周期，避免任务堆积。
- 当前路径前方检测到新占用时，不等下个周期，立即触发一次重规划。

### 平滑不能让路径穿过障碍

每次 Smac 输出后进行轻量处理：

1. 去除重复点。
2. 等弧长重采样，间距约 0.04–0.06 m。
3. 只做少量迭代的曲线平滑。
4. 对平滑后的每个点和线段重新做 footprint 碰撞检查。
5. 检查曲率不超过车辆实际极限。
6. 将新旧路径前方约 0.5–0.8 m 做渐进衔接。

如果平滑后碰撞，就减小平滑强度；仍不通过则使用未经平滑但可行的 Smac 路径，不能因为追求平滑而破坏安全性。

### 尽量不停车的故障处理

我同意不应该因为一次 TF 查询失败或一次规划失败就停车。控制策略调整为：

- 短暂 TF 失败：使用缓存的连续 `odom → base_link` 位姿继续控制。
- 单次规划失败：保留旧路径，下一周期重新规划。
- 新路径校验失败：不替换旧路径。
- AMCL 修正：不直接把跳变传给 PID，而是在下次路径更新时平滑吸收。
- 旧路径前方出现障碍：根据可见净空逐渐减速，同时高频重规划。
- 只有“旧路径已被阻断、Smac 连续找不到绕行路线、刹车距离即将不足”才停车。

这里必须保留最后停车保护。障碍物如果完全封死通道，不停车只能撞上去；目标应该是把停车从“常见恢复动作”降为“不可绕行时的最后动作”。

### 为什么会定位跳变

`odom → base_link` 一般是连续的；真正容易跳的是 AMCL 发布的 `map → odom`。AMCL 并不是连续积分，而是根据新雷达扫描重新匹配地图，因此可能突然修正位置。

当前配置中有几个潜在来源：

- AMCL 使用的是差分底盘运动模型，而车辆是阿克曼底盘。[nav2(rpp_follower).yaml](/root/D_Robot/dev_ws/config/nav2/nav2(rpp_follower).yaml:360)
- 车辆高速转弯、轮胎侧滑时，里程计预测与真实运动不同。
- 赛道墙体或通道形状相似，粒子可能从一个相似位置切换到另一个位置。
- 锥桶等动态障碍被 AMCL 当成地图结构参与匹配。
- `update_min_d: 0.10`、`update_min_a: 0.10` 会使修正呈现一定的分段感。
- 当前仅使用 60 根激光束参与匹配，高速、遮挡较多时信息可能不足。
- EKF 使用了原始 IMU 的绝对 yaw；若 IMU 航向存在磁干扰或跳变，会传到 `odom → base_link`。[ekf_test.yaml](/root/D_Robot/dev_ws/config/localization/ekf_test.yaml:70)
- 雷达、里程计、IMU 时间戳不同步或多个节点重复发布同一 TF。

控制侧最有效的处理是：

> Smac 在 `map` 坐标系规划；接受路径时，把路径变换到连续的 `odom` 坐标系，PID 在 `odom` 中跟踪。

这样 AMCL 的瞬时 `map → odom` 修正不会立刻让 PID 看到车辆“横跳”。新的地图修正会通过下一条 Smac 路径和路径融合逐渐吸收。

### 路径为什么可能无效

“无效”不是指 Smac 经常会生成错误路径，而是新路径上线前需要防御性校验。常见情况包括：

- 规划期间 costmap 恰好更新，路径中的某段已经被新障碍占据；
- 起点因为定位修正落进障碍膨胀区；
- 障碍间距小于车辆 footprint 和安全余量；
- 终点朝向与最小转弯半径组合不可达；
- 规划达到时间或迭代上限；
- 平滑算法把曲线切进障碍物；
- 新旧路径差异太大，直接切换会造成转向阶跃。

这些情况只会拒绝“新候选路径”，不会删除当前有效路径。

### 修订后的实施计划

1. 创建独立 `smac_pid_follower` C++ 包。最初的 `A*_PID` 目录名包含 `*`，不适合作为 ROS 包名。
2. 建立竞速专用 Nav2 参数，只启动地图、AMCL、global costmap、Smac planner；不启动 controller server 和局部规划器。
3. 实现异步 Smac 重规划：定时 3–5 Hz，障碍阻路时立即触发。
4. 实现路径轻量平滑、碰撞检查、曲率检查和新旧路径渐进融合。
5. 参考测试代码复用路线投影、单向进度推进、50 Hz 循环和直接 `/cmd_vel` 输出。[visual_lidar_path_follower.cpp](/root/D_Robot/test/dev_ws/src/origincar_system/src/visual_lidar_path_follower.cpp:479)
6. 实现曲率前馈、横向 PID、航向 PID、抗积分饱和和转向变化率限制。
7. 根据曲率、障碍净空、规划延迟和可见刹车距离连续调速。
8. 在 `odom` 坐标系执行高频跟踪，隔离 AMCL 的瞬时修正。
9. 记录规划平均/P95 延迟、路径切换幅度、横向误差、最小障碍净空和圈速。
10. 依次以 0.4、0.7、1.0 m/s 提速验证，再确定比赛最高速度。

还需要明确一个物理限制：任何规划器都无法提前看到被墙体完全遮挡的障碍。因此比赛速度必须受“当前可见自由距离”约束：

```text
可见自由距离 ≥ 感知/规划延迟行驶距离 + 制动距离 + 安全余量
```

直道视野远就高速，盲弯可见距离短就提前适当收速；这比局部规划器反复犹豫更稳定，也比始终固定高速安全。

### 两种定位方案对比

| 项目 | AMCL | 当前 `lidar_process` |
|---|---|---|
| ROS 版本 | ROS 2/Nav2 | ROS 1/catkin |
| 全局重定位 | 有 | 基本没有 |
| 定位不确定度 | 粒子与协方差 | 协方差全部写成 0 |
| 初值偏差恢复 | 较强 | 容易陷入局部最优 |
| 局部计算速度 | 中等 | 可能更快 |
| 对对称赛道 | 可能多峰，但可恢复 | 容易匹配到错误峰值 |
| 适合作为当前主定位 | 是 | 否 |

`lidar_process` 本质上是一个栅格距离场上的局部扫描匹配器：不断尝试 ±1 栅格和 ±1°，找到分数更高的位置。[lidar_loc.cpp](/root/D_Robot/dev_ws/src/lidar_process/src/lidar_loc.cpp:205)

它目前有几个关键问题：

- 是 ROS 1/catkin 包，不能直接并入当前 ROS 2 控制链路。[CMakeLists.txt](/root/D_Robot/dev_ws/src/lidar_process/CMakeLists.txt:1)
- 地图回调会把初始位置重新设置为 `(0,0,0)`。[lidar_loc.cpp](/root/D_Robot/dev_ws/src/lidar_process/src/lidar_loc.cpp:119)
- 没有使用里程计预测作为每帧搜索初值。
- 使用最新 TF，而非严格按照雷达帧时间戳进行匹配。
- 匹配质量没有可靠阈值，错误匹配也可能继续发布。
- 输出协方差全部为零，相当于宣称定位绝对准确。[lidar_loc.cpp](/root/D_Robot/dev_ws/src/lidar_process/src/lidar_loc.cpp:408)
- 直接发布 `map → odom`，不能与 AMCL 同时运行。[lidar_loc.cpp](/root/D_Robot/dev_ws/src/lidar_process/src/lidar_loc.cpp:391)

### AMCL 会不会太慢

只要架构正确，AMCL 不会限制 PID 频率：

```text
轮速 + IMU → EKF → odom 位姿 30–50 Hz → PID 控制
雷达 + 地图 → AMCL → map→odom 全局纠偏
```

PID 不需要等待 AMCL 每次更新。AMCL 即使只有 8–10 Hz，也只负责修正车辆在地图上的长期位置；车辆每个控制周期的连续运动来自 `odom`。

当前 AMCL 的 `update_min_d=0.10`、`update_min_a=0.10` 确实偏保守，车辆需要移动 10 cm 或转动约 5.7° 才触发更新。[nav2(rpp_follower).yaml](/root/D_Robot/dev_ws/config/nav2/nav2(rpp_follower).yaml:387)

竞速版本建议初始调整为：

```yaml
update_min_d: 0.04
update_min_a: 0.04
max_beams: 90
do_beamskip: true
```

动态锥桶较多时，beam skip 可以减少非静态物体对地图匹配的干扰，但必须通过实车记录验证。

### 最终推荐结构

- Smac 在 `map` 中实时规划。
- 接受新路径时，将其变换到 `odom`。
- PID 在 `odom` 中以 50 Hz 跟踪，避免 AMCL 修正直接造成方向跳变。
- AMCL 更新只影响下一次 Smac 规划，新旧路径通过融合平滑过渡。
- 后续把 `lidar_process` 移植成 ROS 2 后，只发布候选位姿，不直接发布 TF，与 AMCL并行记录比较。
- 只有当它在定位误差、延迟、跳变次数和失锁恢复上全面优于 AMCL，才切换为主定位。

## 主要问题

### [P0] 底盘转向指令语义尚未确定

当前底盘驱动只是把 `/cmd_vel.angular.z` 乘 1000 后直接发给 STM32，并没有在驱动侧根据轴距转换成前轮转角。[origincar_base.cpp](/root/D_Robot/dev_ws/src/drivers/chassis_driver/src/origincar_base.cpp:99)

因此现在无法确认 `angular.z` 在固件中究竟代表：

- 角速度 rad/s；
- 舵机/转角归一化量；
- 实际前轮转角；
- 某种经验控制量。

在没有确认前，不能直接使用：

```text
omega = v × tan(delta) / wheelbase
```

当前参数也存在运动学矛盾：

```text
wheelbase = 0.30 m
max_steering_angle = 0.60 rad
```

对应最小转弯半径约为：

```text
Rmin = 0.30 / tan(0.60) ≈ 0.44 m
```

但 Smac 配置是 `minimum_turning_radius: 0.32`，可能规划出 PID 无法执行的急弯。[nav2(rpp_follower).yaml](/root/D_Robot/dev_ws/config/nav2/nav2(rpp_follower).yaml:273)

必须先通过低速画圆实验标定：

```text
固定速度 × 多组 angular.z
→ 测量实际圆半径
→ 得到 angular.z 到曲率的真实映射
```

然后让 Smac、路径校验器和 PID 使用同一个真实最小半径。

### [P0] 当前单线程执行器会破坏“规划与控制解耦”

节点现在使用普通 `rclcpp::spin()`，即单线程执行。[smac_pid_node.cpp](/root/D_Robot/dev_ws/src/smac_pid/src/smac_pid_node.cpp:64)

以后如果 Smac action 回调、路径平滑或碰撞校验耗时 100–200 ms，50 Hz PID 定时器也会一起暂停。底盘超过约 300 ms 没收到命令还会触发驱动超时停车。

应使用：

- `MultiThreadedExecutor`
- 独立 control callback group
- 独立 planning callback group
- 路径处理工作线程
- 双缓冲或短锁原子替换路径
- 控制线程绝不等待 Smac、TF 长等待或平滑器

::code-comment{title="[P0] 单线程会阻塞 50 Hz 控制" body="普通 rclcpp::spin 会让规划结果处理、路径平滑与控制定时器串行运行。应改为 MultiThreadedExecutor 和独立 callback groups，控制线程只读取已验证路径快照。" file="/root/D_Robot/dev_ws/src/smac_pid/src/smac_pid_node.cpp" start=64 end=68 priority=0}

### [P0] `/cmd_vel` 控制权必须唯一

比赛流程中至少可能存在：

- `visual_control`
- `smac_pid`
- Nav2 velocity smoother
- 键盘控制节点

它们如果同时发布 `/cmd_vel`，底盘只会执行最后收到的消息，表现为突然摆动和速度跳变。

应建立明确控制权：

```text
视觉阶段：visual_control 获得控制权
扫码完成：visual_control 完全停止发布，smac_pid 接管
Smac 路段结束：smac_pid 停止发布，visual_control 恢复
```

最好增加一个轻量 command mux 或控制权状态机，底盘永远只订阅一个最终输出话题。

## 新旧路径切换审查

固定 `path_blend_distance: 0.70` 不够安全。[smac_pid.yaml](/root/D_Robot/dev_ws/src/smac_pid/config/smac_pid.yaml:19)

如果障碍就在车前 0.4 m，而路径融合仍坚持沿旧路径 0.7 m，就会把车带向障碍。

正确策略是：

1. 检查旧路径前方的碰撞距离。
2. 如果旧路径安全，保留一小段共同前缀，平滑切换。
3. 如果旧路径已经阻塞，融合长度必须缩短到障碍前。
4. 新路径与车辆当前转向差过大时，先降速但继续行驶。
5. 平滑后的路径重新使用完整 footprint 检查，不能只检查中心点。

“规划失败继续旧路径”也只能在旧路径刹车范围内仍安全时成立。

## PID 和速度规划审查

参考代码中的路线投影、索引只向前推进、50 Hz 循环可以复用，但控制部分需要升级为：

```text
转向 = 曲率前馈
     + 横向误差 PID
     + 航向误差反馈
```

速度上限取以下最小值：

```text
目标最高速度
曲率允许速度
横向误差允许速度
可见自由距离对应的制动速度
路径新鲜度允许速度
转向变化率允许速度
```

`min_tracking_speed: 0.20` 不能无条件使用。以下情况必须允许降至零：

- 终点；
- 前方安全距离不足；
- 车辆朝向与路径严重相反；
- 所有候选路径都穿过障碍；
- 控制权尚未获得。

## 定位链路审查

推荐链路保持：

```text
轮速 + IMU → EKF → odom→base_link
雷达 + 静态地图 → AMCL → map→odom
```

分工如下：

- Smac 使用 `map` 坐标系和 AMCL 全局定位。
- PID 使用连续的 `odom` 位姿。
- 新路径接受时从 `map` 转换到 `odom`。
- AMCL 修正不能直接让 PID 当前参考路径瞬移。
- 下一条 Smac 路径逐渐吸收新的全局修正。

这部分设计是合理的。AMCL 不需要达到 50 Hz；PID 不应直接依赖 AMCL 每帧输出。

TF 短暂失败时可以使用缓存的 `odom→base_link`，但缓存必须有最大时间，例如 100–200 ms。超过时间继续盲跑，风险会迅速增大。

## 启动与故障流程

不建议继续完全依赖固定的 4、6、8、12 秒启动延迟。应检查：

1. EKF 已发布 `odom→base_link`。
2. map server 已 active。
3. AMCL 已 active 且 `map→odom` 可用。
4. planner server 已 active。
5. global costmap 已收到地图和至少一帧雷达。
6. Smac 已成功生成第一条可行路径。
7. 控制权已经交给 `smac_pid`。
8. 最后才允许发布运动指令。

运行中优先级应为：

```text
正常：跟踪最新有效路径
规划失败：沿安全旧路径继续 + 立即重试
AMCL 短暂修正：odom 中继续控制
TF 短暂失败：短时间使用缓存位姿
旧路径被挡：降速 + 高频重规划
新路径出现：安全拼接后切换
无安全路径且进入制动距离：最后才停车
```

## 最终判断

方案方向正确，尤其是这三点：

- 去掉高频犹豫的局部规划器；
- Smac 与 PID 异步运行；
- AMCL 管全局、odom 管连续控制。

但上车前必须完成：

1. 标定底盘 `angular.z → 实际曲率`。
2. 统一 Smac 最小转弯半径和控制器能力。
3. 改为多线程、规划与控制真正解耦。
4. 增加路线门点管理，防止 Smac 抄近路。
5. 建立唯一 `/cmd_vel` 控制权。
6. 让旧路径复用受碰撞距离和制动距离约束。

当前 `smac_pid` 仍是安全骨架，编译和启动成立，但完整控制闭环尚未实现；在上述边界明确后再进入实际编码是合理顺序。

### Codex（过程更新）

你的猜测有一部分是对的：`0.25 m` 的 Smac 终点容差在 `0.8–1.0 m` 的滚动目标里确实偏大，但图里更像是“终点选在障碍物附近/后方，而代价层对绕行的吸引不足”，不只是路径被拟合成直线。我先放大检查图中参考路线、Smac 路径和膨胀区的相对关系，再对照规划与平滑参数定位主因。

### Codex

你的猜测大约对了一半。图里橙色目标点明显落在障碍物或膨胀区附近，绿色路径在膨胀区边缘就结束了。

关键问题有三个：

1. `tolerance=0.25 m` 确实偏大  
   当滚动目标被障碍物占据时，Smac 可以把障碍物近侧、距离目标不足 25 cm 的位置当作成功终点，所以它没有动力规划到障碍物后方。

2. Smac 并没有拟合整条参考路线  
   当前只把“前方 1 米的一个点”交给 Smac，中间参考路线并未作为约束。因此它只考虑最短可行路径，很容易切弯、走直线。

3. 当前参数明显偏向直行

- `non_straight_penalty=2.2`：转弯惩罚较强
- `inflation_radius=0.25`：安全区偏小
- `cost_scaling_factor=3.5`：障碍代价衰减较快
- 路径校验只拒绝 `cost=254`，允许进入灰色膨胀区

但只把容差从 `0.25` 降低并不能彻底解决：如果目标点就在障碍物里，结果会从“停在近侧”变成“规划失败”，仍然不会绕过去。

正确方案应当是：

- 正常情况下仍使用 `0.8–1.0 m` 前瞻，避免直角弯切弯。
- 检测到目标点或前方参考路线被障碍物占据时，临时沿路线向后寻找障碍物之后的安全目标点。
- 让这个临时目标至少位于障碍物后方约 `0.3 m`，Smac 才会生成完整绕行弧线。
- 同时把目标容差降至 `0.10 m`。
- 增大膨胀半径并降低转弯惩罚，例如：

```yaml
tolerance: 0.10
non_straight_penalty: 1.20
cost_penalty: 4.50
inflation_radius: 0.35
cost_scaling_factor: 2.5
```

所以最主要的原因不是“平滑拟合成直线”，而是滚动目标可能落在障碍物附近，加上 25 cm 容差，让 Smac 在障碍物近侧提前完成规划。最佳修复是“正常短前瞻 + 遇障碍自动把目标延伸到障碍物后方”。

### Codex

增加到 `0.35 m` 是因为你之前反馈路径太贴障碍物，希望 Smac 更早感受到障碍物代价并主动转弯。

但在新的滚动窗口逻辑中，它可能偏保守：

- 膨胀区：`0.35 m`
- 离开膨胀区后再前进：`obstacle_away=0.20 m`
- 恢复约束点距离障碍物约为 `0.55 m`

而且现在所有膨胀区内的路线点都会被删除，因此膨胀半径越大，删除的路线点越多，绕行也越远。

所以更合理的初始组合其实是：

```yaml
inflation_radius: 0.25
obstacle_away: 0.20
```

这样恢复点大约在障碍物外 `0.45 m`，对比赛场地更灵活。`0.35 m` 是针对之前“贴障碍物”的加强措施，不是新滚动窗口必须的参数。建议先恢复 `0.25 m`，只验证新的多点约束逻辑，避免一次改变太多变量。
